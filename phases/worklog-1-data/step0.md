## 작업

### 1. `docs/ADR.md`
- 맨 끝에 `### ADR-0NN: 업무일지 — 업무사항 서버 저장, 자동 저장, 엑셀 양식 예외, 칸 글자 저장, 바뀐 칸만 저장` 하나(지금 있는 글의 제목을 고친다). 번호는 파일의 마지막 번호 + 1
- **결정** 다섯(design.md 5·7·8·9·10·12·16절 요약)
  - **업무사항은 서버(`worklog_days`의 `memo` 칸)에 저장한다 (사용자).** 모든 PC가 같은 글을 보고 어느 PC에서든 인쇄되고 휴대폰에서도 보인다(보기만, 승인된 로그인). AI로 보내지 않는다. 남는 위험: 환자 이름은 자동으로 못 막는다 → 흐린 안내 글 "환자 이름·차트번호는 적지 않아요"와 모양 막기(전화·주민번호·메일, 모든 입력 칸)로 줄인다. **CLAUDE.md CRITICAL '서버·Claude API에는 집계 숫자만 간다'의 업무일지 예외**임을 적는다: 사람이 손으로 적는 일지 글이고 비트 환자 자료가 아니다(환자 자료 구역 규칙은 그대로다)
  - **서버 칸은 적으면 자동 저장한다 (사용자).** 저장 단추가 없다. 입력을 800ms 묶어 `worklog_days`에 바로 저장하고, 못 하면 값을 화면에 둔 채 알린다. 브라우저 저장소에 임시 사본을 두지 않고, 저장 안 된 값이 있으면 떠나기 확인을 묻는다 **(Claude 판단)**
  - **업무일지 양식 칸은 엑셀 서식 예외다 (사용자 결정에서 나온 Claude 판단).** (지금 글 그대로)
  - **숫자 칸은 친 글자를 저장한다 (사용자).** 칸에 글자도 적고, 합계는 짐작하지 않는 규칙으로 읽은 숫자로만 낸다. 금액 정수 규칙(`plan.md` §5)의 업무일지 예외이고 합계는 그대로 원 단위 정수다
  - **바뀐 칸만 저장한다 (사용자).** 두 PC가 같은 날을 고치면 다른 칸은 둘 다 남고 같은 칸은 나중 저장이 이긴다. 다른 PC 글은 화면이 60초마다·다시 보일 때 다시 읽어 보인다(실시간 연결은 쓰지 않는다)
- `plan.md` §10 '입력값 임시 저장'과의 관계 한 줄(서버 칸은 임시 저장이 아니라 바로 저장이다, 지금 글 그대로). ARCHITECTURE '브라우저 저장소에는 폴더 핸들만 둔다'와의 관계 줄은 지운다(이제 예외가 아니다. 업무일지는 브라우저 저장소를 쓰지 않는다)
- **이유**: 업무일지를 여러 PC에서 쓰고 같은 업무사항을 봐야 한다 **(사용자)**. 사용자는 환자 이름·차트번호를 적지 않는다 **(사용자)**. 올린 옛 엑셀의 업무사항 칸에는 적혀 있었으므로 안내 글이 필요하다 **(Claude 확인)**. 저장 단추 없이 적으면 저절로 저장되기를 바랐다 **(사용자)**. 양식은 "엑셀이랑 완전 똑같이" **(사용자)**. 칸에 글자도 적고 싶다 **(사용자)**
- **트레이드오프**: 업무사항에 이름이 적히면 서버에 남는다(자동으로 못 막는다). 같은 칸을 두 PC가 고치면 앞 글이 사라지고 바꾼 기록이 없다(지난 날 잠금·고친 사람·시각 기록도 없다, 사용자 결정. 동시 수정 막기는 §10 2차). 숫자 칸은 DB가 숫자 범위를 지켜 주지 못하고, 다른 명세가 쓰려면 같은 읽기 규칙을 거쳐야 한다. 다른 PC 글이 최대 60초 늦게 보인다. 양식 칸은 Pretendard·400~600 굵기·토큰 규칙의 예외다 → 색 토큰 넷과 CSS Module 한 파일로 가둔다

## 금지사항

- ADR 번호를 미리 정해 다른 문서에 박지 마라. 이유: 다른 갈래와 번호가 겹칠 수 있어 합칠 때 다시 매긴다(design.md 18절)
- 다른 갈래·이전 작업이 쓴 ADR·규칙 문장을 지우거나 고쳐 쓰지 마라(꼬리표 빼고). 이유: 다른 갈래와 합칠 때 겹침이 커지고, 규칙은 그대로 다른 화면에 적용된다
- `specs/` 아래 파일(requirements·design·tasks·approval·tdd-log)을 고치지 마라. 이유: 승인 해시가 바뀌면 승인이 풀려 모든 구현이 막힌다. 명세와 다른 점을 찾으면 고치지 말고 summary에 적는다
- 위 '수정 범위' 밖의 파일을 만들거나 고치지 마라. 이유: SDD 훅이 막고 Stop 점검이 '범위 밖'으로 실패한다. 꼭 필요하면 `blocked`로 멈추고 어떤 파일이 왜 필요한지 적는다
- 시험을 지우거나, 건너뛰거나(`skip`·`only`), 기대값을 약하게 바꿔 통과시키지 마라. 이유: AC와 시험의 연결이 끊겨 명세를 지켰는지 알 수 없게 된다
- 실제 Supabase에 SQL을 실행하거나 붙여 넣지 마라(대시보드·CLI·REST 모두). 이유: DB 바꾸기는 사용자 OK가 필요하다(design.md 8절)
- 시험·고정 자료에 실제 의원 숫자(엑셀 10월 값)·환자 이름·차트번호·전화번호를 쓰지 마라. 이유: 가짜 자료만 쓴다(CLAUDE.md). 둥근 가짜 숫자(예: 100000)와 "가상" 글자를 쓴다
- `git commit`·`git push`를 하지 마라. 이유: 커밋은 harness-reviewer PASS 뒤에 execute.py(또는 메인 세션)가 한다
- `.harness/*`·`CLAUDE.md`를 고치지 마라. 이유: 이 step의 범위가 아니다
