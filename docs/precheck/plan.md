# 청구 사전점검 plan

`PRD.md`(무엇을·왜)를 어떻게 만들지 적은 문서다. 2026-10-30 기준이다. 루트 `plan.md`와 `CLAUDE.md`가 이긴다. 다만 아래 5절에 적은 항목은 명세와 ADR(설계 결정 기록)에서 사용자 승인을 받아 바꾼다.

## 1. 구조

```
[우리 웹사이트 화면]  ──메시지──▶  [우리 크롬 확장]  ──메시지──▶  [도우미 (윈도우 프로그램)]  ──읽기·입력──▶  [비트 DB · 비트 화면]
       │                     (우리 사이트 주소만 받음)        (크롬이 필요할 때 켬)
       │                                                       └─ PC 확인 창, 작업 저장(암호화)
       └── 건수·설정만 ──▶ [서버 (Supabase)]
```

- **연결 방식** **(사용자: 크롬이 알아서 켜는 도우미)**. 크롬 "네이티브 메시징"을 쓴다. 크롬과 PC 프로그램이 직접 대화하는 공식 통로다. 그래서 다음 세 가지가 없다.
  - PC에 열린 문(포트)이 없다.
  - 크롬 "로컬 네트워크 허용" 창이 뜨지 않는다.
  - 열쇠값을 주고받지 않는다.
- **양지바른과 연결하지 않는다** **(사용자)**. 양지바른의 C# 코드 중 비트 읽기와 자동 입력 부분만 우리 도우미로 옮긴다.

| 크롬 확장 | 우리 사이트에서 온 메시지만 도우미에 넘김 | 이 저장소의 새 폴더. 크롬 웹스토어에 **비공개(unlisted)**로 올린다 |
| 도우미 | 비트 DB 읽기(읽기 전용), 비트 자동 입력, PC 확인 창, 작업 중 내용·완료 표시 저장, 요양기관기호 확인 | 이 저장소의 새 폴더(C#/.NET, 윈도우). 양지바른 `vendor/drbit_export`·`vendor/secure_bridge`에서 옮긴다 |

## 4. 보안 (Claude 판단)
- **확장:** 우리 사이트 주소(정해 둔 origin)에서 온 메시지만 받는다. 도우미는 우리 확장의 메시지만 받는다.
- **도우미:** 정해 둔 명령만 받는다. 명령은 자료 읽기, 입력 요청, 저장, 버전이다. 입력 요청은 **PC 확인 창**에서 [확인]을 눌러야 실행한다 **(사용자)**. 그 창의 '이제부터 묻지 않기'를 PC에서 켜면 청구 창을 닫을 때까지 창을 생략한다(2026-11-01 사용자, `specs/precheck` REQ-037). 매번 요양기관기호가 등록한 병원과 같은지 확인한다.
- **서버:** 건수 표는 DB 제약으로 숫자만 받는다. 환자 정보가 글자로 섞여 들어갈 칸을 만들지 않는다.
- **청구 화면:** 오류 수집 도구를 달지 않는다.
- **계정:** GitHub·Vercel·크롬 웹스토어 계정에 2단계 로그인을 켠다.
- **자리 비움 잠금은 없다** **(사용자)**.

## 5. 지금 규칙과 부딪히는 것 (명세·ADR에서 정함)
- **루트 `plan.md §10`**: 사용자가 뺐던 "청구·삭감 관리"와 "청구메모 exe"를 2026-10-30 사용자가 다시 꺼냈다.
- **`CLAUDE.md` 환자 자료 구역**: `lib/parsers`·`lib/analytics`·`lib/payload`·`workers`에서 네트워크를 막는 울타리가 있다. 확장에서 받은 환자 자료가 어느 코드를 거쳐 Worker로 가는지 정한다. 그 통로 코드는 서버·저장소·console을 못 쓰게 울타리를 친다. ADR이 필요하다.
- **새 기술**: 크롬 확장, C#/.NET 도우미, 윈도우 빌드. `CLAUDE.md` 기술 스택과 ADR에 넣는다.
- **CSP**: 네이티브 메시징은 `connect-src`와 상관없다. 확장 ID를 부르는 코드만 허용 목록에 넣는다.

## 6. 만드는 순서: Phase · Step
- **승인은 한 번만 받는다** **(사용자: "단계마다 sdd 승인받는거 빼줘")**.
  - Phase 0에서 전체 명세(`/sdd`)와 전체 화면 목업을 한꺼번에 만들고, 사용자가 한 번 승인한다. `CLAUDE.md`가 구현 전 명세 승인과 화면 목업 승인을 요구하기 때문이다.
  - 그 뒤 Phase 1~7은 멈추지 않고 이어서 만든다(사용자 Phase 방식).
- **Step 하나 = 모듈 하나.** 시험을 먼저 쓰고(RED), 통과시키고(GREEN), 리뷰어 PASS를 받으면 커밋한다.
- **Phase가 끝날 때마다** 다음을 한다.
  1. 자동 시험(`verify`)을 돌린다.
  2. 바뀐 화면 캡처(PC·휴대폰)를 남긴다.
  3. 쉬운 말로 보고한다.
  4. **의원 PC 시험 목록**을 드린다. 사용자가 시험하고 결과를 알려 주시면 고친다.
     - 의원 PC 시험은 저장소 시험과 따로다. 저장소 시험(자동 시험·골든 테스트·화면 캡처)은 `fixtures/`의 가짜 자료만 쓴다(`CLAUDE.md`).
     - 의원 PC 시험은 사용자가 그 PC에서 실제 자료로 직접 한다. 환자 자료를 저장소·채팅·서버에 올리지 않고, 복사하거나 화면 사진으로 남기지 않는다. 결과는 '같음/다름'과 건수만 알려 주신다(이름·차트번호·전화·화면 사진 없이).
- **멈추고 묻는 경우는 중요한 결정뿐이다.** 범위 변경, 돈이 드는 일, 배포·합치기, 같은 실패가 계속될 때만 멈춘다.
- **먼저 있어야 하는 것:** 앱 틀(탭 바, 로그인)은 `auth` 작업이 끝나 있어야 한다. 청구 화면은 그 틀 안의 새 탭이다.
- **Step 파일:** 각 Step의 자세한 작업 지시는 `phases/precheck-N-*/stepK.md`에 쓴다. 이 목록을 사용자가 OK한 뒤 Phase 0에서 만든다.

## 7. 위험과 Phase 1에서 먼저 확인할 것
- **비트 DB 접속**: 양지바른이 비트 설치 위치와 DB를 찾는 방식(`InstallationLocator`·`ReadOnlyConnection`)을 그대로 옮겨 의원 PC에서 확인한다.
- **비트 자동 입력**: 양지바른의 화면 조작 코드(FlaUI 기반 `UChartAutomation`)를 옮긴다. 가장 큰 작업이다. Phase 3 전에 짧은 시험을 먼저 해 본다.
- **크롬 웹스토어 비공개 등록**: 구글 개발자 등록(5달러, 사용자 계정)과 심사에 며칠이 걸린다. Phase 1을 시작할 때 바로 신청한다.
- **메시지 크기**: 도우미에서 크롬으로 가는 메시지는 한 번에 1MB까지다. 12개월 이력은 나눠 보낸다.
- **빌드**: 이 서버(리눅스)에서는 윈도우 프로그램을 실행할 수 없다. 그래서 GitHub의 윈도우 빌드 기능(GitHub Actions)으로 도우미를 만들고, 사용자는 받아서 시험만 하는 방식을 제안한다(Claude 제안, Phase 0 명세에서 확정). 서명하지 않은 프로그램이라 처음 실행할 때 윈도우 경고가 뜰 수 있다.
- **출처 결과와 같게**: 같은 가짜 자료를 넣었을 때 양지바른과 우리 앱의 점검 결과·메모가 같은지 시험(골든 테스트)으로 확인한다.
