# 설계: 환자 탭: F/U 명단 읽는 기간을 120일에서 30일로

## 구성 요소
- `src/workers/patients/plan.ts`: `FOLLOWUP_DAYS` 120 → 30. `followupPlan`의 나누기 식은 그대로 둔다(30 ≤ `MAX_PIECE_DAYS` 31이라 늘 조각 하나). `recallPlan`은 손대지 않는다
- `src/workers/patients/jobs.ts`: 고치지 않는다. `buildFollowup`의 `read`가 `FOLLOWUP_DAYS`를 쓰므로 저절로 30일이 된다
- `src/components/patients/PatientsScreen.tsx`: 읽는 중 안내(30행 `note`)를 "최근 30일을 읽어요. 다 읽을 때까지 이 창을 열어 두세요."로 바꾼다. 화면 짜임은 그대로이고 글자만 바뀐다. 그래서 새 클릭 목업을 만들지 않고, 목업 `docs/mockups/patients/index.html`의 같은 글자를 함께 바꾼다. 이 명세 승인을 그 글자 승인으로 본다
- 가짜 자료 `fixtures/patients/make-fake-patients.ts` `followupPieces()`: F/U 조각 넷(07-06~11-02) → 하나(`2026-10-04`~`2026-11-02`, 오늘 2026-11-02 기준 30일). 사례는 남기고 날짜만 안으로 옮긴다
  - 01 마지막 내원만: 앞 내원 V0101 `2026-07-10` → `2026-10-06`
  - 06 지난 예정: V0102 `2026-07-10` → `2026-10-05`(예정 10-12, 오늘보다 앞)
  - 07 날짜 미정: V0201 `2026-08-20` → `2026-10-20`
  - '자료 없는 조각' 사례는 조각이 하나라 없어진다
  - `npm run fixtures`로 `fixtures/patients/fake/targets-followup.json`을 다시 만든다. 다른 가짜 파일이 바뀌면(줄 끝 등) 되돌린다
- 시험: `plan.test.ts`(F/U 쪽 AC-604.2 시험을 AC-2401.1로), `handler.test.ts`(조각 여러 개를 전제한 시험 — 둘째·넷째 조각, 앞 조각 빼기 — 을 조각 하나와 계획에 없는 기간으로 바꾼다. 뜻은 그대로), `jobs.test.ts`(바뀐 날짜 기대값), `PatientsScreen.test.tsx`(안내 글)

## 데이터 흐름
변함없음: 화면 → Worker `plan`(F/U 조각 하나 + 정기 주사 달 조각) → 통로 → 도우미 → 조각 → Worker `build`. 비트 F/U 읽기가 4번에서 1번으로 준다

## 결정과 트레이드오프
- 상수 하나만 바꾼다(가장 작은 변경). 기간을 설정으로 빼지 않는다(사용자가 고르게 하는 것은 범위 밖)
- 결과: 마지막 내원이 31~120일 전인 환자는 F/U 명단에 나오지 않는다(예: 6주·8주 뒤 예정, 31일 넘게 지난 예정). 사용자 결정이다
- 같은 환자가 31일보다 전에 왔고 30일 안에 다시 왔으면 30일 안의 내원만 본다(전과 같은 '마지막 내원' 규칙)

## 위험
- 조각 여러 개를 다루는 Worker 코드(F/U 쪽)는 실제로는 한 조각만 받게 된다. 코드는 그대로 두고(정기 주사가 같은 길을 쓴다) 시험은 정기 주사 쪽이 여러 조각을 계속 다룬다
- 다른 창 "환자 탭 로딩 지연"이 같은 파일을 만질 수 있다 → 시작 전에 알렸다
