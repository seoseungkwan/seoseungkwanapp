# 요구사항: 어느 메모든 고치기 (완료·같음 메모도 고치고, 목록의 메모 줄마다 [메모 고치기])

> 기능 ID: `memo-edit-any` · 형식: 요구사항은 `### REQ-2201: 제목`, 수용 기준은 `- AC-2201.1: Given/When/Then`.
> 각 AC 는 테스트 하나 이상으로 검증되어야 하며, 테스트 이름에 AC ID 를 넣는다.
> 사용자: "계획은 최소화해" — 짧게 쓴다. 이름·글은 모두 지어낸 값이다(가상환자 A·B, 글 T·E).

## 배경 / 목표
- 2026-11-06 사용자 결정(대화, 아래 '이미 정한 것'). 승인 기록(`approval.json`)은 사용자가 `/sdd approve memo-edit-any`를 입력해 남긴다. 화면 목업(design.md '화면 목업')은 사용자가 따로 승인한다
- 청구 화면 메모 표의 칸은 `readOnly={locked || row.done}`이다(`rows/MemoTable.tsx:69`). `done`은 완료한 사람(완료 표시·입력 기록 done) 또는 비교가 '같음'인 사람이다(`workers/precheck/jobs.ts:544`). 그런데 칸 모양은 보통 칸(`ds.input`)이라 쳐도 아무 일이 없다. 이 잠금을 정한 AC는 없다(precheck AC-018.1은 상태를 보일 뿐, AC-014.11은 다시 만들지 않기)
- 입력할 사람·빠지는 사람 목록의 [메모 고치기]는 확인 필요·지난번 건너뜀 줄에만 있다(`rows/MemoRows.tsx:195-204`, precheck AC-018.26). 이 명세가 그 부분을 넓힌다. precheck 명세 파일은 고치지 않는다
- 지키는 precheck 규칙: AC-014.11(설정이 바뀌어도 사람이 고친·완료한 메모는 다시 만들지 않음), AC-018.2(고친 글은 1초 뒤 그 PC에 저장), AC-018.14(다른 메모는 '메모 바꿈'·[바꾸지 않기]), AC-037.1(바꾸기 전 원래 메모는 도우미가 그 PC에 남김)
- 도우미(C# 프로그램)는 고치지 않는다. 완료한 사람을 다시 보내도 도우미는 거르거나 거절하지 않는다(design.md '도우미 영향'). 새 도우미 배포가 없다

## 이미 정한 것 (다시 묻지 않는다)
1. 완료 메모와 비트와 '같음'인 메모도 고칠 수 있다. 고치면 그 사람의 '완료'가 풀리고, 다음 입력에서 비트 메모를 고친 글로 바꾼다('메모 바꿈', 지금의 `replaces` 길). 고쳐도 다른 메모를 다시 만들지 않는다
2. 목록에서 메모 글이 있는 줄마다 [메모 고치기]가 있다. 입력하는 동안에만 막힌다. 메모 없는 줄에는 없다. 지금 있는 단추([바꾸지 않기]·[이 메모로 바꾸기]·[다시 하기]·[먼저 고치기])는 그대로다
3. 입력하는 동안은 고칠 수 없고, 막힌 칸은 읽기 전용 모양(`ds.readonly`)으로 보인다

## 요구사항

### REQ-2201: 메모 표에서 완료·같음 메모도 고친다
- AC-2201.1: Given 메모 표에 상태 '완료' 줄과 비교 '같음' 줄, When 입력 중이 아닐 때 그리면, Then 두 줄의 메모 칸은 `readOnly`가 아니고 다른 줄과 같은 보통 칸(`ds.input`)이다. 글을 치면 `onChange`, 칸 밖을 누르면 `onBlur`가 불린다(저장은 지금처럼 1초 뒤 `editMemo`)
- AC-2201.2: Given 확인 기다리는 중·입력 중(`locked`), When 그리면, Then 모든 줄의 메모 칸이 `readOnly`이고 읽기 전용 모양이다(`ds.readonly`의 클래스가 모두 있고 `ds.input`의 `bg-surface`·`border-line-strong`이 없다). `locked`가 풀리면 다시 보통 칸이다
- AC-2201.3: Given 완료였다가 고친 줄(Worker가 `done: false`·`edited: true`·비교 '다름'으로 보냄), When 그리면, Then 상태 칩은 '고침', 비교 칩은 '다름'이고 [아직 입력 안 된 것만]을 눌러도 그 줄이 남는다

### REQ-2202: 고친 완료 메모는 완료가 풀리고 다음 입력에서 비트 메모를 바꾼다
- AC-2202.1: Given 완료한 A(그 달 파일 `done[A]` = 넣은 글 T, 입력 기록 done, 비트 메모 T), When A를 E로 고치면(`editMemo`), Then 그 달 `store.save` 한 번에 `drafts[A] = E`·`done[A] = false`가 가고 다른 사람의 drafts·done 값은 받은 그대로다. 다음 메모 보기에서 A는 `done: false`·비교 '다름'이고 입력할 사람에 칩 '메모 바꿈'·`replaces` T로 들며, [비트에 입력] 묶음의 A 줄은 `{ visitKey, chart, name, date, memo: E, replaces: T }`다
- AC-2202.2: Given 완료 기록 없이 비교가 '같음'인 B(비트 메모 T), When B를 E로 고치면, Then `store.save`의 done은 받은 그대로이고(drafts만 바뀐다) B는 입력할 사람에 '메모 바꿈'·`replaces` T로 든다
- AC-2202.3: Given 이 화면에서 비트 메모를 읽은 뒤 입력을 마친 A(사본의 비트 메모는 입력 전 값, 예: 비어 있음), When A를 E로 고치면, Then 비교에 쓰는 비트 글은 그때 넣은 글 T이고 A는 '메모 바꿈'·`replaces` T다. T가 4,000자를 넘으면 읽지 못한 것('조회 못함')이다. 고치지 않은 완료 줄의 비교와, 성공한 비트 메모 다시 불러오기 뒤의 비교는 지금처럼 읽은 글로 한다
- AC-2202.4: Given 완료한 사람, When 고치지 않거나(비트 메모가 뒤에 바뀌어 '다름'이어도) 지금 글과 같은 글의 `editMemo`가 오면, Then 지금처럼 '이미 입력됨'이고 묶음에 없으며 `store.save`도 없다
- AC-2202.5: Given 달 파일에 `done[A] = false`·`drafts[A] = E`, 입력 기록 done, When 다시 [자료 불러오기]를 하면(store.load), Then A는 완료가 아니고 글은 E이며 AC-2202.1과 같은 줄이다(`false`는 완료 표시가 아니다). 다음 저장에도 `done[A] = false`가 그대로 간다
- AC-2202.6: Given 풀린 A를 넣은 입력, When 끝 답에서 A가 '완료'이면, Then `done[A] = E`(글)로 저장되어 다시 '완료'다. '건너뜀'·'확인 필요'이면 풀린 채(`done[A] = false`) 남는다
- AC-2202.7: Given 고친 뒤 저장이 실패한 채(`E-STORE-FAILED`) 고친 메모를 남기고 다시 불러와(`keepEdits`) 달 파일은 옛 `done[A] = T`, When 달 칸을 받으면, Then 고친 글 E와 함께 완료 풀림도 다시 얹혀 A는 완료가 아니고 다음 저장에 `done[A] = false`가 간다
- AC-2202.8: Given 풀린 A(E)·손대지 않은 C·완료한 D, When 설정을 바꿔 다시 점검하면, Then C만 새로 만들어지고 A는 E, D는 완료 글 그대로다. A를 고쳐도 다른 사람의 글·완료는 바뀌지 않는다

### REQ-2203: 목록의 메모 줄마다 [메모 고치기]
- AC-2203.1: Given 입력할 사람·빠지는 사람 목록, When 그리면, Then 우리 메모 글이 있는 줄(`hasMemo`이고 공백뿐이 아님)마다 [메모 고치기]가 하나 있다: 입력할 사람(새 메모·메모 바꿈)과 이미 입력됨·확인 필요·직접 입력·다른 메모 있음·비트 메모를 읽지 못함·지난번 건너뜀 줄. 메모 없음 줄과 글이 공백뿐인 줄에는 없다
- AC-2203.2: Given [메모 고치기], When 누르면, Then `onEdit(key)`가 불린다. 그 줄이 `editing`이면 [메모 고치기] 자리에 지금 칸(`{이름} 메모 고치기`, 처음 값은 우리 메모)이 있고 칸 밖을 누르면 `onEditDone(key, 글)`이다. 같은 줄의 다른 단추는 그대로 보인다
- AC-2203.3: Given 입력 중(`locked`), When 그리면, Then 모든 [메모 고치기]가 막힌다(disabled). 비트 메모 읽는 중(`reading`)·`startBlocked`로는 막지 않는다
- AC-2203.4: Given 지금 있는 단추, When 그리면, Then [바꾸지 않기](메모 바꿈 줄)·[이 메모로 바꾸기](다른 메모 있음 줄)·[다시 하기 (N명)]는 지금 자리·이름·막힘 그대로이고, [메모 고치기]는 [바꾸지 않기]·[이 메모로 바꾸기]의 오른쪽 같은 줄에 있다. 묶음 이름·까닭 글은 그대로다

### REQ-2204: 도우미·울타리·지금 시험은 그대로
- AC-2204.1: Given 풀린 사람을 넣는 묶음과 고친 저장, When 보내는 글자를 보면, Then `bit.input` 줄의 칸은 `visitKey`·`chart`·`name`·`date`·`memo`·`replaces`뿐이고 `store.save`는 `month`·`drafts`·`done`뿐이다. 새 명령·새 칸이 없고 `helper/**`·`src/lib/bridge/commands.json`·`MIN_HELPER`는 바꾸지 않는다
- AC-2204.2: Given `components/claim/rows`의 두 파일, When 고친 코드를 보면, Then 줄은 props로만 받고 새 불러오기는 `@/lib/precheck/memoCompare`의 `isBlankMemo` 하나뿐이다. `src/guardrails.test.ts`와 `npm run lint`가 그대로 통과한다. 고친 글과 완료 풀림은 Worker → 통로 → 도우미(그 PC의 암호화 파일)로만 가고 서버에는 가지 않는다
- AC-2204.3: Given 지금 시험, When 이 기능 뒤에 돌리면, Then 기대값을 바꾸지 않고 통과한다(`jobs.test.ts`의 '입력 기록이 done이면 비교가 다름이고 … 이미 입력됨' 포함). 예외는 시험 이름 하나뿐이다: `MemoRows.test.tsx`의 "'메모 바꿈' 줄에는 [바꾸지 않기]만 있고"를 "[바꾸지 않기]·[메모 고치기]만 있고"로 고친다(기대값 그대로)
